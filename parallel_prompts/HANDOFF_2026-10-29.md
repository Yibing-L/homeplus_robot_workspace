# HomePlus pickup — handoff for the next agent (2026-10-29)

You are continuing work on the HomePlus robot (Cornell Architectural Robotics Lab).
Goal: `pick_up_coffee` (pick up a red Solo cup from a table) runs end to end on the
real robot, driven entirely from the operator console UI. Work happens on a native
Ubuntu laptop (Alienware, NVIDIA GPU) — the previous setup was a Mac + Ubuntu VM.

## System overview

- ROS 2 Humble, MoveIt 2 (KDL IK, OMPL RRTConnect), OctoMap (0.02 m resolution).
- `homeplus_vision`: MolmoPoint (pointing) + SAM2 (mask) target detection
  (`scripts/grounding_dino_node.py`, run as `molmopoint_node.py`), and
  `obstacle_cloud_node.py` that builds the OctoMap input cloud from the hand D405.
- `homeplus_moveit_config`: `scripts/gesture_motion_executor.py` executes commands
  from `config/gesture_execution_map.yaml` (`pick_up_coffee` is a 9-step sequence:
  open_gripper, retract_arm_for_pickup, move_to_pregrasp, refine_target,
  align_refined_grasp, move_to_grasp, close_gripper_at_target, lift, retreat_with_object).
- `homeplus_console`: FastAPI + rclpy backend, React UI (http://<host>:8080). The
  user drives the robot from here. Operator must "Take control", tick the two
  declarations ("One target object in view", "Area clear") — they reset whenever the
  executor restarts — then Start. Each trajectory needs approval in the UI.
- Arduino Mega firmware (closed loop): elbow/shoulder have AS5600 encoders (3°
  tracking limit), wrist/hand/gripper are open-loop servos. Board reset drops the arm
  ~1 s then raises it, and zeroes base odometry.
- Hand camera: Intel RealSense D405 (mounted on the hand; pose comes from TF/URDF).

### Mac-only pieces you do NOT need on native Ubuntu

  (the obstacle node's 9-frame median is the main fix either way).
- `tools/arduino_serial_bridge/` (socat) → use the Arduino serial port directly
  (`arduino_port:=/dev/ttyACM0` or similar).
- Remote inference: on the Mac, MolmoPoint/SAM2 ran on a cloud GPU via
  `remote_inference_url` in `homeplus_vision/config/target_detection_params.yaml`.
  Leave it `""` on the Alienware to run locally (needs roughly ≥8 GB VRAM for
  4-bit MolmoPoint-8B + SAM2; run `scripts/setup_molmopoint.sh` first).

## How it was launched (VM, adapt paths)

```
ros2 launch homeplus_moveit_config gesture_control.launch.py arduino_port:=<port> launch_obstacle_cloud:=false use_octomap:=true
ros2 launch homeplus_vision vision_pipeline.launch.py side_mount:=left task_id:=1 enable_target_detection:=true enable_gesture_detection:=false enable_d405_octomap:=true enable_d435i_octomap:=false enable_d455_octomap:=false
```
(On the Mac, `enable_d405:=false` because the bridge published the camera; on Ubuntu
let the launch start the D405.) Plus the console (`homeplus_console`).

## Dry run (plan everything, move nothing) — do this before any real run

Run a second executor with `dry_run: true` and its own topics:
```
ros2 run homeplus_moveit_config gesture_motion_executor.py --ros-args -r __node:=gesture_dry_run --params-file ~/dryrun_params.yaml
ros2 topic pub --once /gesture_dry_run/command homeplus_interfaces/msg/GestureCommand "{gesture_id: 0, gesture_label: dry_run, confidence: 1.0, command_name: pick_up_coffee, command_type: sequence}"
```
`dryrun_params.yaml` = the executor params with `dry_run: true`, `plan_only: true` and
every topic remapped under `/gesture_dry_run/`. Echo `/arduino/command_queue` and
`/arduino/stop` during the run to prove nothing was sent. Note: a dry run never moves
the camera, so steps 4+ are planned from the far view (less realistic).

## What we found (measured, not guessed)

1. **D405 depth noise on the table was the main blocker.** At ~0.8–1 m the D405
   (rated 7–50 cm) sees the table at a grazing angle: per-pixel depth jumps ~35–49 mm
   frame to frame (tails 57–73 mm); the camera-facing cup is ~5 mm. The executor
   clears the OctoMap before each plan and rebuilds from 1–2 frames, so outliers
   became voxels 2–8 cm above the table ("stuff above the green table" in RViz) and
   the palm "collided". FIX (committed): `depth_median_frames: 9` in
   `obstacle_clouds.yaml` — per-pixel median over 9 settled frames (~2 s at 5 fps,
   reset on motion). After it, the table under the hand path stays ≤0.68 m and the
   dry run planned all 9 steps.
2. **Palm geometry.** `palm_1` reaches ~4.7 cm below the grasp TCP. On a 12 cm Solo
   cup (measured extent ~0.70→0.82 m world), a mid-height grasp leaves the palm only
   ~1.3 cm above the table — less than one 2 cm voxel. `cup_min_palm_clearance_m`
   (detector) raises the grasp so the palm keeps a margin above the cup's measured
   bottom. It is 0.03 now; the last real run failed pre-grasp with the palm 1 cm over
   a table voxel → **raise to 0.04** (next step B). Do not use blanket offsets — the
   user rejected "+2 cm"; height must come from measurement.
3. **Far vs close detection disagree by ~4–5 cm sideways every run** (e.g. far
   (0.993, 0.253) vs close (0.957, 0.203)). `refine_target` then exceeds its 20 mm
   arm-plane limit and does a full retract + base re-place ("dumb retract" the user
   hates). Likely hand-camera extrinsic (URDF/TF) error that varies with arm pose.
   **Next step A: calibrate the hand camera** (cup at known positions, compare far
   vs close detections and to tape measurements).
4. **Table box** (`homeplus_vision/table_plane.py`): the table is fitted as a level
   plane (height only; full 3D fits were skewed by noise) anchored on the surface
   under the cup, published as collision object `detected_table`, and its band
   removed from the voxel cloud. Points inside the cup's own cylinder are removed too.
5. **Lift failures after grasp** (fixed in executor, committed, verified only by
   tests so far): the attached cup touched `detected_table` (start state invalid) →
   ACM now allows `detected_cup`↔`detected_table`; fingers touched the cup's own
   voxels → ACM allows fingers↔`<octomap>` while holding (reverted on gripper_open).
6. **Grasp height source**: `refine_target` now takes Z from the close-up detection
   (`preserve_reference_z: false`); the far view had put the grasp at the rim.
7. Camera calibration/pose was checked and is steady (pitch 20.1–20.7°, z 1.127–1.131
   m between frames); "the table looks tilted" earlier was a bad multi-surface fit,
   not the camera.
